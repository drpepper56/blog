Telegram Mini App Parcel Shipment Tracking

Typescript + Rust + MongoDB + 17Track API

A simple mobile app made using the Telegram mini app environment to get detailed tracking information and push notifications about order updates through telegram. The motivation behind this project was a nomination at a hackathon I went to last year, a team of one won with a project that integrated a Solana wallet into telegram using a mini app.

scan the QR code to open the app in telegram

Client

github repository

The app is written in typescript with basic CSS, it works as a single page application, elements are swapped in and out of view to show different sides of the app. Telegram Bots make it possible to run website-like applications natively on telegram, the bot is used to manage notifications, client server URLs and much more.

Authentication is done using the telegram account, so the user never sees a register or login page, the account is liked to the user’s telegram user ID, which is stored on the server in its raw form and as a hash digest for telegram notification and authentication purposes.

There are currently 3 ways to open the app, the OPEN button in the telegram chat window on the bot, a direct link from the QR code. These two open the app normally, which is when it loads the user’s tracked packages list. The third way is through an update notification, then the program loads only the data of the package from the notification and upon going back to the main screen it pulls all the data from the server.

Registering a tracking number can be done currently up to 4 times for free due to the API cost. If the API was not able to detect the carrier, the user will need to specify it, they can search for the carrier from a long carrier list supported by the API so it’s really easy to add it.

Users have an option to give a name tag to a tracking number like “new TV” or “running shoes”. To avoid database overhead, telegram cloud storage was used to store them, it only allows up to 1024 key-value pairs so it’s not scalable, but it’s enough for a proof of concept. The name tags are retrieved the same way as the tracking data, get only the relevant name tag if opening a notification, then get the rest when going to the tracking list.

The main page of the app is a list of tracking numbers that display the username tag, tracking number and latest event description. Clicking one of those windows shows all shipping events. At the bottom of the page, the buttons give the user options to subscribe or unsubscribe to tracking updates and remove the tracking number from their list, which cannot be undone.

Name tags can be changed when clicking on them on the details page, if no name tag is set, a default blue text will let the user know they can set it.

Server

github repository

The server is written in rust using Actix Web package to run the server, records and tracking data is stored on Atlas MongoDB, the tracking data is obtained from 17Track API endpoint. Heroku is used for hosting the server and the client static content.

All API calls are managed from a separate file trackingapi.rs, the API uses HTTPS requests for communication, the data is received in the response JSON body. Responses from the API are processed in trackingapi.rs to make it simple in the main.rs. Error responses are converted into a custom Error enum based on the API error codes and context, success responses return the JSON as a structure.

Data about users stored on the database is their telegram ID, hashed telegram ID and the tracking quota remaining, set to 4 when creating a user. The API has different data structured for the response JSON depending on the request, tracking data stored in the database is formatted to only have relevant information.

Updates are delivered to users through the telegram bot, which they work like text messages, the user gets a push notification on their phone, and they can open the notification in the bot chat window. The system is limited in what it allows in the body, the most that can be sent is a message to the user and a tracking number parameter to the client so it can request the tracking data.

Ideas for further development

Cross user sharing of tracking pages - Give users an option to share tracking from a number they have registered to someone from their contacts or a phone number. The receiver would be able to view the tracking page or add the number to their account and receive updates on it.

Add the username tag to the push notification - If it’s possible to do an injection method for values stored in the telegram cloud into the bot notification message, the username tag can be included in the notification. Alternatively, the name tag can be moved to the database to the collection that holds relations between the users and tracking numbers.

Register a tracking number when highlighting it - Send a tracking number to the telegram bot in the chat window from the options you get on your phone when highlighting text. The bot would need to resolve text messages as a tracking number parameter and run the register function in the app.

Google Data Analytics Capstone Project

R + Tableau

A walkthrough and rationale of steps taken in completing the capstone project for Google Data Analytics Certification on Coursera. Data was cleaned and transformed using R dplyr, visualizations were made using Tableau. Full transformation script, data source and a more numerical documentation is available at the end of this article.

The subject of the dataset is a urban bike renting company from Chicago, the data only includes records of trips and the attributes do not hold any user information. Loading the huge data set from separate csv files to one data frame in R was done using a recursive function that took a list of files and returned the data frame.

Cleaning and Transformation

Data Inconsistencies were found in the names and ID values of stations.

All names were trimmed of spaces, prefixes and suffixes in names, “Temp” or “Public Rack” where removed if the same ID was found without the extra text. In some cases the names prefixed with “Public Rack” had the same IDs but a different group of coordinate values, making their difference valid, the IDs from that group were prefixed with PR to preserve that data. After that there were 8 inconsistencies left, some had unique suffixes that were removed, random numbers were replaced with matching IDs. The remaining conflicting stations that had the same ID but were different were fixed by adding a D prefix to the ID value of the group with less entries. ID inconsistencies were easily fixed after the previous step by assigning the majority ID value to the whole group.

Missing values were found in columns that describe the start and end station name and ID number, station longitude and latitude.

Four significant figures after the decimal point was chosen as the minimum for an accurate value for latitude and longitude, which is around 11 meters error margin, this didn’t expand the already existing error margin of records showing different coordinates for the same station, which was up to 60 meters in some tested cases. Records with missing names or IDs of stations were given the values of records with accurate coordinate matches. This didn’t make any change. The same was done in reverse, giving coordinate values to fields with matching name and ID of a station, and a few end station coordinates were filled in.

The combined time field was split into separate time and date field to make it easier to work on. Records that had missing time or date or start time recorded chronological after the end date, were removed. A field for trip duration was added

Where the coordinates were accurate enough a distance field was added, otherwise it was set to NA. Records with distance zero and both start and end station set and different to each other were removed.

From the distance and time fields, a field was created for the trip’s average speed.

Outlier Removal

Outlier values only happened in numerical fields for distance, time and speed.

Trips with duration over 90’000 seconds and under 7 seconds were removed.

A few trips with over 50 kilometers were in a group with around 9’800 kilometers values, they were removed.

Speed was analysed separately for electrical and regular bikes, electric bike trip speed was capped at 8.3 meter per second and 7.5 meters per second for regular bikes. No lowest speed limit was set.

Most of these limit values were found by looking at the shape of distribution graphs and identifying the point after which the number of trips didn’t follow the distribution curve or dropped significantly.

Data Analytics

Assumptions and different data sets

In the final complete set there are missing values in trip distance and speed, and in the start and end station name and ID.

The set with any station missing has a massive difference of electric bike to classical bike trips, 852 thousand to 1.4 thousand for members and 517 thousand to 4.5 thousand for casual users.

The set with no missing station, but missing values in distance and speed didn’t have any bias towards either electric or classical bikes

This bias can influence the data and it needs to be taken into account when choosing the right set for analysis on speed values. To avoid skewing the results analysis on speed values should be done in averages and be separated for classical and electrical bikes.

To normalise the analysis and for the sake of consistency the starting station will be used as the location reference point for the trip.

A general analysis of the data split between classical and electric bikes, shows that trips done by members are on average faster and have shorter times than those done by casual users, for both classical and electric bikes alike.

There is one preference trend for the type of bike, casual users taking electrical bikes more than classical bikes, which happens in morning rush hours 6am to 9am and is also present, but slightly weaker in the afternoon between 3pm and 6pm.

Plotting the station on the map shows a distribution of density of the trips taken by casual users and members.

The north residential side of the Chicago Metropolitan area between the Lake Michigan and North Branch Chicago River starting at Lincoln Park going up to Montrose Point Bird Sanctuary, has many member trips as well as casual trips.

The casual users’ trips in the selected area show trends similar to members’ trips in the whole sample, shorter trip times and faster average speed.

Other areas looked at that didn’t show this trend in casual trips were the south University Area around Hyde Park and a selection of stations that have at least 20 casual trips started in the morning or afternoon rush hours. The north city/residential area is the best choice for a targeted marketing campaign, and it should focus on casual users that clock higher trip speeds, with shorter trip times.

Analysing the average distance of trips on weekdays in and outside the selected area in the north side of Chicago show that members in the area complete around 35% longer distance trips in the morning rush hours compared to members outside the selected area. The casual user group in the selected area is completing around 25% longer distance trips on average compared to their counterpart outside the selected area in the morning rush hours. This trend can further help to identify casual users that complete longer distance trips and would be more likely to purchase a membership in the selected area.
